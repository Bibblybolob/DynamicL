# Fix the 13-Minute Background Coma After a Real Pause — Implementation Plan

> **For Hermes:** Use subagent-driven-development skill to implement this plan task-by-task.

**Goal:** Eliminate the 13-minute silent gap in polling that begins ~65s after a *real* pause while locked, so the app recovers within seconds of playback resuming (song change, play press) without needing an unlock.

**Architecture:** The stall-hold fix (`697c683`) works — both new stale-API stalls were ridden out at 0.7s cadence with no coma. The remaining coma is a different mechanism: after a real pause, `manageKeepAlive()` stops the audio session; iOS then suspends the process on its own schedule (~60s later), and once suspended nothing can wake it except user foregrounding. The fix is to keep a minimal keep-alive alive through real pauses for a bounded window (mirroring Spotify's own behavior: paused-but-alive), so any resume is caught instantly; plus a watchdog that detects "API says playing but polls stopped" and re-arms the keeper.

**Tech Stack:** Swift / AVFoundation audio session / ActivityKit / existing DiagnosticsLog pipeline.

## Root cause

`manageKeepAlive()` (AppModel.swift:317-330) runs `keeper.stop()` whenever state ≠ playing (and not stall-held). With the audio session deactivated, the app has zero background entitlement left; iOS suspends it roughly a minute later. Any resume event while locked lands in a suspended process: Spotify's API changed, but nobody's listening until iOS decides to wake us (which for this app effectively means unlock/foreground).

The 697c683 fix covered *fake* pauses (stale-API lies). This is the *real*-pause variant of the same failure: we still need to hear the resume.

## Proposed approach

1. **Paused-grace keep-alive:** treat a *recent* real pause like the stall hold — keep the silent audio running for up to **120s** after pausing (configurable constant). Covers the dominant use case ("paused, will resume within a couple minutes"); bounded battery cost.
2. **Wake watchdog:** when status says playing but no poll has landed for >6s, force `keeper.start()` again (self-heal if iOS killed the session anyway) and log `watchdog: revive`.
3. **Diagnostics:** log transitions `pause grace started/ended`, `watchdog: revive` so next trace proves which mechanism held/woke.

### Task 1: Paused-grace window in AppModel.manageKeepAlive (TDD where testable)

**Objective:** Keep the process alive ≤120s after a real pause so a locked-phone resume is heard.

**Files:**
- Modify: `DynamicallyricsApp/App/AppModel.swift` (manageKeepAlive ~line 317, add two stored props near line 408)

**Step 1: Add state + logic**

```swift
@ObservationIgnored private var lastPlayingAt: Date = .distantPast
/// How long after a REAL pause we keep the keep-alive running so a resume
/// (play press / skip from the lock screen) is heard instead of landing in a
/// suspended process. iOS suspends us ~60s after the audio session dies.
static let pausedKeepAliveGrace: TimeInterval = 120

private func manageKeepAlive() {
    let now = Date.now
    if status?.state == .playing { lastPlayingAt = now }
    let stalled = provider?.shouldHoldKeepAlive ?? false
    // Recent real pause still counts: we must keep listening for resume.
    let recentlyPlaying = now.timeIntervalSince(lastPlayingAt) < Self.pausedKeepAliveGrace
    let shouldRun = (auth.isConnected || demoActive)
        && (status?.state == .playing || stalled || recentlyPlaying)
        && lockScreenLyricsEnabled
    if shouldRun {
        keeper.start()
    } else {
        keeper.stop()
        if !recentlyPlaying { /* grace fully elapsed */ }
    }
}
```

/// Status says playing but data went quiet: something killed polling (audio
/// session revoked, hung socket that slipped past the 12s ceiling). Re-arm.
private func revivePollerIfNeeded() {
    guard status?.state == .playing,
          let last = provider?.lastSuccessfulPollAt,
          Date.now.timeIntervalSince(last) > 6 else { return }
    provider?.start()          // start() guards on pollTask == nil internally? verify:

}

## Risks / tradeoffs / open questions

- **Battery vs responsiveness:** 120s of silent audio per pause is the same cost class Apple allows navigation apps; bounded and small. If Jonathan wants longer lock-screen control responsiveness, raise the constant; the LA already ends at 300s regardless.
- **Watchdog restart semantics:** cancelling a hung URLSession task mid-flight is safe; recreating the poll task must not double-schedule (verify the `pollTask == nil` guard path).
- **The `la=false` anomaly** may be its own small bug (Task 3 note); fix only if confirmed by logs during verification, as a follow-up commit.
- Unresolved question: whether iOS suspends despite the active audio session if volume-gated; if the 798s gap recurs *with* grace active, next lever is `AVAudioSession.interruptionNotification` logging + moving to a `beginBackgroundTask` extension as belt-and-braces.
